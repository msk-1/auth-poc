SPA × Web API の認証・認可をリリースする前に確かめる項目を、構成要素ごとにまとめる。括弧内は詳しく扱った章である。

既定の構成

同一オリジンの BFF + 認可コードフロー + PKCE + HttpOnly セッション Cookie + JWT を検証する Web API を既定とする。BFF を置けない場合だけブラウザ内方式を選び、下の「ブラウザ内方式の追加項目」も満たす（04）。

認可サーバー

  • Implicit と Resource Owner Password グラントを無効にした（01）
  • PKCE を必須にし、方式を S256 に限った（02）
  • リダイレクト URI をクライアントごとに完全一致で登録した。ワイルドカードを使っていない
  • アクセストークンの寿命を 15 分以下にした
  • API ごとに aud を分け、クライアントに許すスコープを最小にした
  • ブラウザに渡すリフレッシュトークンにローテーションと絶対期限を設定した（06）

BFF / クライアント

  • state、nonce、code_verifier をログインのたびに暗号用乱数で作り、照合している（02）
  • ID トークンの署名、iss、aud、exp、nonce を検証している（03）
  • ユーザーの紐付けを iss + sub で行っている。email を使っていない
  • セッション Cookie に __Host-、HttpOnly、Secure、SameSite=Lax 以上を付けた（06）
  • 状態を変えるリクエストに CSRF 対策（カスタムヘッダーまたはトークン、Origin の確認）を入れた
  • ログイン後にセッション ID を作り直している（セッション固定攻撃の対策）
  • ログアウトで、BFF のセッション破棄、リフレッシュトークンの失効、IdP のログアウトを行う（03）
  • 設定値をディスカバリから取得している

ブラウザ内方式の追加項目

  • トークンを localStorage / sessionStorage / JavaScript から読める Cookie に置いていない（06）
  • クライアントシークレットを SPA に埋め込んでいない（01）
  • 厳格な CSP を配信している（06）
  • コールバック後に URL から code と state を消している
  • DPoP の採用を検討した（06）

Web API

  • 署名、alg（許可リスト）、iss、aud、exp、typ を検証している（05）
  • エンドポイントごとにスコープを確かめている
  • リソースの所有者を sub で確かめている（BOLA 対策、05）
  • 401 と 403 を正しく使い分け、WWW-Authenticate を返している（05）
  • CORS を明示したオリジンに限った。* や Origin の反射をしていない（06）
  • JWKS をキャッシュし、未知の kid で取り直す。鍵ローテーションを試験した（03）

運用

  • トークン、認可コード、code_verifier をログやエラーレポートに出していない（06）
  • ログイン失敗、リフレッシュトークンの再利用検知、401 / 403 の急増を監視している
  • 依存ライブラリ（OIDC クライアント、JWT 検証）を定期的に更新している
  • クライアントシークレットや署名鍵の入れ替え手順を決めてある
