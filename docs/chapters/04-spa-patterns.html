SPA × Web API の構成の違いは、トークンをどこに置くかに尽きる。機密性の高いデータを扱うなら、トークンをブラウザに置かない BFF を選ぶ。

SPA の難しさ

ブラウザは、同じページで動くすべての JavaScript を同じ権限で動かす。自分のコードも、依存ライブラリも、XSS で注入されたコードも区別しない。したがって、ページの JavaScript から触れるトークンは、XSS が起きたら攻撃者にも触れる。

この前提から、IETF のドラフト「OAuth 2.0 for Browser-Based Applications」は 3 つの構成を、安全な順に示している。

3 つの構成

A. BFF（Backend for Frontend）

SPA と同じオリジンに置いたサーバー（BFF）が、Confidential client として OAuth のフローを回す。トークンは BFF のセッションに保管し、ブラウザには HttpOnly のセッション Cookie だけを渡す。SPA からの API 呼び出しは BFF が中継し、アクセストークンを付けて Web API へ送る。

  • XSS が起きてもトークン自体は盗まれない。ただし攻撃者は、被害者のブラウザから BFF 経由で API を呼べる（セッションの乗っ取り）。XSS 対策は依然として必要である
  • Cookie を使うので、CSRF 対策が必要になる（06 章）
  • SPA と BFF が同一オリジンなら、CORS は不要になる

B. Token-Mediating Backend

バックエンドが OAuth のフローを回し、リフレッシュトークンは自分で持つ。アクセストークンだけを SPA に渡し、SPA は Web API を直接呼ぶ。

  • リフレッシュトークンは守れるが、アクセストークンは XSS で盗まれ得る
  • API を BFF で中継できない事情（遅延、既存の API ゲートウェイなど）がある場合の折衷案である

C. ブラウザ内クライアント

SPA 自身が Public client として認可コード + PKCE を回し、トークンをブラウザ内に持つ。oidc-client-ts や各 IdP の SDK が使う方式である。

  • 静的ホスティングだけで動き、構成が最も簡単
  • XSS が起きると、アクセストークンとリフレッシュトークンの両方を盗まれ得る。盗まれたトークンは攻撃者の環境から使える
  • 採用するなら、リフレッシュトークンのローテーション、短い寿命、厳格な CSP を必須にする

番外: BFF と API の一体型

A〜C は、SPA がアクセストークンで Web API を呼ぶことを前提にしている。しかし、API が SPA 専用で、SPA と同じサーバーに置けるなら、BFF と API を 1 つのアプリにまとめられる。ログインにだけ OIDC を使い、その後はサーバー側のセッションで本人を識別する。従来型の Web アプリと同じ構成である。

  • 自分の API にアクセストークンは要らない: 認可コードフローでログインし、ID トークンを検証したら、セッションにユーザーを結び付ける。API の各エンドポイントは、セッションのユーザーで認可する
  • トークンをセッションに持つのは必要なときだけ: 外部 API（別のリソースサーバー）を呼ぶならアクセストークンとリフレッシュトークン、RP-Initiated Logout で id_token_hint を送るなら ID トークンを持つ
  • ブラウザにはトークンが一切出ない: BFF と同じく、XSS でトークンを盗まれることはない。ただし、セッションの乗っ取りは防げないので XSS 対策は要る
  • 中継が要らない: BFF のように API 呼び出しを転送する層がないので、構成が最も単純になる

Spring Security なら oauth2Login() とセッションで成り立ち、oauth2ResourceServer()（Bearer トークンの検証）は使わない（作例）。

@Bean
SecurityFilterChain security(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(a -> a
            .requestMatchers("/", "/assets/**").permitAll()
            .anyRequest().authenticated())
        .oauth2Login(Customizer.withDefaults());
    // CSRF 保護は既定で有効。SPA からトークンを送るための設定は、
    // 使っているバージョンの Spring Security の公式ドキュメントに従う
    return http.build();
}

注意点は次のとおりである。

  • CSRF 対策が必須: Cookie で認証するので、SameSite、CSRF トークン、カスタムヘッダーの必須化を組み合わせる（06 章）
  • 同一オリジンで配信する: SPA の静的ファイルを同じサーバーか同じリバースプロキシから配る。別ドメインにすると Cookie と CORS の扱いが難しくなる
  • セッションはサーバー側のストアに置く: Cookie にはセッション ID だけを入れる。複数台にするならセッションを共有する（Spring Session + Redis など）
  • 他のクライアントから使いにくい: モバイルアプリや外部システムから同じ API を呼ぶなら、Bearer トークンを受け付ける口が別に要る。その時点で API をリソースサーバーとして分け、A〜C のいずれかに移ることを検討する

選び方

  1. 個人情報、決済、医療、業務データを扱う → A. BFF
  2. API が SPA 専用で、同じサーバーに置ける → BFF と API の一体型（A をさらに単純にした形）
  3. BFF で中継できない明確な理由がある → B. Token-Mediating Backend
  4. 扱うデータの機密性が低く、サーバーを持てない → C. ブラウザ内クライアント（対策を全部入れる）

Service Worker や Web Worker にトークンを閉じ込める方法

C 方式の改良として、トークンを Worker の中だけに置き、ページの JavaScript から直接読めないようにする方法がある。トークンの持ち出しは難しくなるが、XSS で注入されたコードが Worker 経由で API を呼ぶことは防げない。BFF と同じく「乗っ取り」は残る。

まとめ

  • ページの JavaScript から触れるトークンは、XSS が起きれば攻撃者にも触れる
  • BFF はトークンをサーバーに置き、ブラウザには HttpOnly Cookie だけを渡す。既定の選択はこれ
  • API が SPA 専用なら、BFF と API を一体にし、ログインにだけ OIDC を使う構成が最も単純である
  • どの構成でも XSS 対策は要る。BFF は「盗まれる」を防ぐが「乗っ取られる」は防がない
