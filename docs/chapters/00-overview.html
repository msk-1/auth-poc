OAuth 2.0 は認可、OpenID Connect（OIDC）は認証の仕様である。SPA から Web API を呼ぶ構成では、OIDC でユーザーを確かめ、OAuth 2.0 のアクセストークンで API を呼ぶ。

認証と認可

認証（Authentication）認可（Authorization）
答える問い相手は誰か相手に何を許すか
仕様OpenID ConnectOAuth 2.0
主な成果物ID トークンアクセストークン
受け取る人クライアント（SPA や BFF）リソースサーバー（Web API）
失敗したときの HTTP401 Unauthorized403 Forbidden

HTTP の 401 Unauthorized は名前に反して「認証されていない」を意味する。「認証済みだが権限がない」は 403 Forbidden である。

OAuth が解決する問題

OAuth 以前は、別のサービスのデータを使うために、そのサービスのパスワードをアプリに預けていた。この方式には 3 つの問題がある。

  • アプリがパスワードを知るので、何でもできてしまう（権限を絞れない）
  • アプリだけ止めることができない（パスワードを変えると全部止まる）
  • アプリからパスワードが漏れる危険がある

OAuth 2.0 では、ユーザーは認可サーバーにだけパスワードを入力し、アプリには範囲（スコープ）と期限を限ったアクセストークンが渡る。トークンはアプリごとに失効できる。

OAuth 2.0 だけでログインを作らない

アクセストークンは「API を呼んでよい」という証明であり、「誰がこのアプリにログインしたか」の証明ではない。別のアプリ向けに発行されたトークンを持ち込まれても区別できない。ログインには OIDC の ID トークンを使う（03 章）。

登場人物

OAuth 2.0 は 4 つのロールを定める。SPA × Web API に当てはめると次の図になる。

ロール具体例役割
Resource Ownerエンドユーザー自分のデータへのアクセスを許可する
ClientSPA、BFF、モバイルアプリトークンを取得し、API を呼ぶ
Authorization ServerKeycloak、Auth0、Entra ID、Cognitoユーザーを認証し、トークンを発行する
Resource ServerWeb APIトークンを検証し、リソースを返す

OIDC では認可サーバーを OpenID Provider（OP）、クライアントを Relying Party（RP） と呼ぶ。一般には IdP（Identity Provider）とも呼ぶ。

まとめ

  • 認証は「誰か」、認可は「何を許すか」。OIDC が認証、OAuth 2.0 が認可を担う
  • OAuth 2.0 の目的は、パスワードを渡さずに、範囲と期限を限った権限を渡すことである
  • 登場人物は Resource Owner、Client、Authorization Server、Resource Server の 4 つ
