認可コードフローは、ブラウザ経由では使い捨ての認可コードだけを渡し、トークンは直接通信で受け取る。PKCE は、横取りされた認可コードを攻撃者がトークンに交換できないようにする。

流れの全体

SPA が自分でフローを回す場合（04 章の C 方式）で示す。BFF 方式では、SPA の位置に BFF が入る。

1. PKCE の値を作る

ログインのたびに、クライアントは推測できない乱数 code_verifier（43〜128 文字）を作り、そのハッシュを code_challenge とする。

// 作例: ブラウザの Web Crypto API で PKCE の値を作る
function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}

const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));   // 43 文字
const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
const challenge = base64url(new Uint8Array(digest));

code_verifier は手元に残し、code_challenge だけを送る。Math.random() は暗号用の乱数ではないので使わない。

2. 認可リクエスト

ブラウザを認可エンドポイントへ移動させる。

GET /authorize?response_type=code
  &client_id=spa-example
  &redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
  &scope=openid%20profile%20orders%3Aread
  &state=af0ifjsldkj
  &nonce=n-0S6_WzA2Mj
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256 HTTP/1.1
Host: auth.example.com
パラメータ意味
response_type=code認可コードを返してほしい
redirect_uri戻り先。登録済みの値と完全一致しなければ拒否される
scope要求する権限。openid を含めると OIDC になる
stateリクエストとコールバックを結び付ける乱数
nonceID トークンとリクエストを結び付ける乱数（OIDC）
code_challenge / _methodPKCE。方式は必ず S256。plain は使わない

3. コールバック

ユーザーがログインして同意すると、認可サーバーはブラウザをリダイレクト URI へ戻す。

HTTP/1.1 302 Found
Location: https://app.example.com/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj

クライアントは、受け取った state が自分の送った値と一致するかを確かめる。一致しなければ処理を止める。確認したら history.replaceState などで URL から code を消す。

4. トークンリクエスト

POST /token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
&client_id=spa-example
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

認可サーバーは SHA256(code_verifier) を計算し、手順 2 で受け取った code_challenge と比べる。一致すればトークンを返す。

{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCJ9...",
  "token_type": "Bearer",
  "expires_in": 600,
  "refresh_token": "8xLOxBtZp8...",
  "id_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6IjFlOWdkazcifQ...",
  "scope": "openid profile orders:read"
}

BFF（Confidential client）の場合は、このリクエストにクライアント認証（client_secret、または private_key_jwt）も付ける。

PKCE が防ぐもの

認可コードは URL に載るので、漏れる経路がある。ブラウザの履歴、Referer、悪意あるブラウザ拡張、モバイルでは同じカスタム URL スキームを登録した別アプリなどである。

  • PKCE がない場合: 横取りした code をトークンエンドポイントに送れば、攻撃者がトークンを得る
  • PKCE がある場合: code_verifier はクライアントの中から出ていないので、攻撃者は交換できない

PKCE はもともと Public client 向けに作られたが、現在は Confidential client でも使うことが推奨されている（RFC 9700）。認可コードの注入攻撃も防げるためである。

パラメータと防ぐ攻撃

仕組み防ぐ攻撃確認する人
redirect_uri の完全一致認可コードを攻撃者のサイトへ送らせる認可サーバー
stateログイン CSRF（攻撃者のアカウントでログインさせる）クライアント
PKCE認可コードの横取り・注入認可サーバー
nonceID トークンのリプレイクライアント

自分で実装しない

ここで示した手順は理解のためである。実装には実績のあるライブラリ（oidc-client-ts、各 IdP の SDK、サーバー側なら Spring Security や openid-client など）を使う。

リフレッシュ

アクセストークンが切れたら、リフレッシュトークンで新しいものを受け取る。ユーザーの操作は要らない。

POST /token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=8xLOxBtZp8...&client_id=spa-example

Public client に渡すリフレッシュトークンは、使うたびに新しいものに替わる（ローテーション）か、送信者に紐付いている（DPoP）必要がある（RFC 9700）。2 つのトークンの関係とローテーションの流れは 01 章、ブラウザでの対策は 06 章で扱う。

まとめ

  • ブラウザ経由で渡すのは使い捨ての認可コードだけ。トークンは直接通信で受け取る
  • PKCE は code_verifier を知る者だけがコードを交換できるようにする。方式は S256
  • state はログイン CSRF、nonce は ID トークンのリプレイ、redirect_uri の完全一致はコードの持ち出しを防ぐ
