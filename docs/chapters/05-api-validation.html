Web API はリクエストごとにアクセストークンを検証する。署名、発行者、宛先、期限、種類を確かめた後、スコープとリソースの所有者で認可する。検証は自前で書かず、実績のあるライブラリに任せる。

JWT 形式の検証手順

RFC 9068 の JWT アクセストークンを受け取った場合の手順である。

  1. Authorization: Bearer ヘッダーからトークンを取り出す。なければ 401
  2. ヘッダーの alg が許可リスト（例: RS256、ES256）にあるかを確かめる
  3. ヘッダーの kid に対応する公開鍵を JWKS から取り、署名を検証する
  4. iss が信頼する認可サーバーと完全一致するかを確かめる
  5. aud が自分の API の識別子を含むかを確かめる
  6. exp と nbf を確かめる。時計のずれの許容は 60 秒程度にする
  7. ヘッダーの typ が at+jwt であるかを確かめ、ID トークンの流用を弾く

ここまでが「このトークンは本物で、自分宛てで、有効か」の確認である。次の節の認可はこれとは別に行う。

alg の罠

攻撃内容対策
alg: none署名なしのトークンを受け入れさせるnone を許可リストに入れない
アルゴリズム混同RS256 の公開鍵を HS256 の共有鍵として使わせ、攻撃者が署名を作る鍵ごとに使うアルゴリズムを固定する。トークンの alg で検証方法を決めない
jku / x5u の差し替えトークンのヘッダーで攻撃者の鍵の URL を指す鍵はディスカバリの jwks_uri からだけ取る

認可: スコープと所有者

有効なトークンでも、何をしてよいかは別に確かめる。確かめることは 2 段ある。

段問い例
スコープ（クライアントの権限）この操作をクライアントに許したかPOST /orders には orders:write が要る
所有者・ロール（ユーザーの権限）このユーザーがこのリソースを触ってよいかGET /orders/42 は注文 42 の所有者が sub と一致するときだけ

BOLA（Broken Object Level Authorization）

2 段目を忘れると、URL の ID を書き換えるだけで他人のデータが見える。OWASP API Security Top 10 で 1 位の脆弱性である。スコープの確認だけでは防げない。データの取得条件に sub を含める。

// 作例: 所有者を条件に含めて取得する
Order order = orderRepository.findByIdAndOwnerSub(orderId, jwt.getSubject())
    .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));

他人のリソースには 403 ではなく 404 を返すと、リソースの存在自体を隠せる。

不透明トークンの検証

トークンがランダムな文字列なら、イントロスペクションエンドポイントに問い合わせる（RFC 7662）。

POST /introspect HTTP/1.1
Host: auth.example.com
Authorization: Basic YXBpOnNlY3JldA==
Content-Type: application/x-www-form-urlencoded

token=2YotnFZFEjr1zCsicMWpAA

{ "active": true, "sub": "248289761001", "scope": "orders:read", "aud": "https://api.example.com", "exp": 1762590000 }
  • active が false なら 401
  • 失効が即座に効く代わりに、リクエストごとに通信が発生する
  • 結果をキャッシュするなら、トークンの exp を超えない時間にする

失敗時の応答

RFC 6750 は WWW-Authenticate ヘッダーでエラーの種類を返すよう定めている。

状況ステータスWWW-Authenticate
トークンがない401Bearer realm="api"
署名不正・期限切れ・宛先違い401Bearer error="invalid_token"
リクエストの形が不正400Bearer error="invalid_request"
スコープ不足403Bearer error="insufficient_scope", scope="orders:write"

クライアントは 401 を受けたらトークンを更新して 1 回だけ再試行する。403 では再試行しない。

作例: Spring Security

Spring Boot のリソースサーバーでは、issuer-uri を設定するとディスカバリから JWKS を取り、署名・iss・exp を検証する。aud は既定では検証されないので、audiences で指定する。

# application.yml（作例）
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com
          audiences: https://api.example.com

// 作例: スコープで認可する
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(a -> a
            .requestMatchers(HttpMethod.GET, "/orders/**").hasAuthority("SCOPE_orders:read")
            .requestMatchers(HttpMethod.POST, "/orders/**").hasAuthority("SCOPE_orders:write")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(c -> c.disable());   // Cookie を使わない Bearer 専用の API なので CSRF 対策は不要
    return http.build();
}

プロパティ名や既定の挙動は Spring Security の版によって変わる。使う版の資料で確かめる。

まとめ

  • 検証は署名・alg・iss・aud・exp・typ。alg は許可リストで固定する
  • 認可はスコープ（クライアント）と所有者（ユーザー）の 2 段。所有者の確認を忘れると BOLA になる
  • 401 は「トークンが使えない」、403 は「権限が足りない」
