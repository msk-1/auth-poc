OAuth 2.0 は、範囲と期限を限ったアクセストークンをクライアントに発行する仕組みである。SPA で使うグラントは、認可コード + PKCE とリフレッシュトークンの 2 つだけである。

クライアントの種別

クライアントは、秘密（クライアントシークレットや秘密鍵）を守れるかどうかで 2 つに分かれる。この区別が、使えるフローと構成を決める。

種別例秘密を守れるか
Confidential clientサーバーサイドの Web アプリ、BFF守れる。サーバーの中にあり、利用者から見えない
Public clientSPA、モバイルアプリ、デスクトップアプリ守れない。配布したコードは誰でも読める

SPA にクライアントシークレットを埋め込まない

ビルドした JavaScript に埋めたシークレットは、開発者ツールで誰でも取り出せる。SPA は Public client として登録し、シークレットの代わりに PKCE を使う。

エンドポイント

エンドポイント誰が呼ぶか役割
認可エンドポイント（/authorize）ブラウザ（リダイレクト）ユーザーを認証し、同意を得て、認可コードを返す
トークンエンドポイント（/token）クライアント（直接の HTTP POST）認可コードやリフレッシュトークンをトークンに交換する
リダイレクト URI認可サーバーがブラウザを戻す先クライアント側の受け口。事前に登録する
失効エンドポイント（/revoke）クライアントトークンを無効にする（RFC 7009）
イントロスペクション（/introspect）リソースサーバートークンが有効かを問い合わせる（RFC 7662）

認可エンドポイントはブラウザ経由（フロントチャネル）、トークンエンドポイントは直接通信（バックチャネル）である。フロントチャネルの値は URL や履歴に残り得るので、ここにはトークンを流さない。

グラントタイプ

グラントタイプは、クライアントがトークンを得る手順の種類である。

グラント用途SPA × Web API での扱い
Authorization Code + PKCEユーザーが関わるログイン全般使う（02 章）
Refresh Tokenアクセストークンの再取得使う。ブラウザに渡すならローテーションを必須にする
Client Credentialsサービス間通信（ユーザー不在）SPA では使わない。BFF やバッチから内部 API を呼ぶときに使う
Device Authorization入力手段の乏しい端末（TV など）使わない

使わないグラント

グラント問題扱い
Implicitアクセストークンを URL のフラグメントで返すため、履歴・Referer・ブラウザ拡張から漏れる。トークンが正しい相手に渡ったかも確かめられないRFC 9700 で非推奨。OAuth 2.1 で削除
Resource Owner Password Credentialsクライアントがパスワードを直接受け取る。OAuth が解決したかった問題そのもの。MFA とも相性が悪いRFC 9700 で禁止。OAuth 2.1 で削除

かつて SPA は Implicit を使うのが定番だった。ブラウザから別オリジンのトークンエンドポイントを呼べなかった（CORS が普及していなかった）ためである。現在は CORS が使えるので、SPA でも認可コード + PKCE を使う。

トークン

トークン使う相手寿命の目安漏れたときの影響
アクセストークンWeb API5〜15 分期限までの間、API を呼ばれる
リフレッシュトークン認可サーバーのトークンエンドポイント数時間〜数十日新しいアクセストークンを作られ続ける
ID トークン（OIDC）クライアント自身数分なりすましのログインに使われ得る

アクセストークンは Bearer トークンである。持っている人なら誰でも使える。送るときは Authorization ヘッダーに載せる。

GET /orders HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCJ9...

クエリ文字列（?access_token=...）では送らない。サーバーのアクセスログやプロキシに残る。

トークンの形式

OAuth 2.0 はアクセストークンの形式を定めていない。実際には次の 2 つがある。

形式検証方法長所短所
JWT（RFC 9068）API が署名を自分で検証する認可サーバーへの問い合わせが不要で速い期限前に失効させにくい
不透明トークン（ランダムな文字列）API が認可サーバーに問い合わせる失効が即座に効くリクエストごとに通信が発生する

クライアントはアクセストークンの中身を読まない。形式は認可サーバーと API の間の取り決めであり、クライアントから見ると単なる文字列である。

アクセストークンとリフレッシュトークン

なぜ 2 つに分けるのか

トークンが 1 種類しかないと、次の 2 つの要求がぶつかる。

  • 漏れたときの被害を小さくしたい → 寿命を短くしたい
  • ユーザーに何度もログインさせたくない → 寿命を長くしたい

OAuth 2.0 は、役割の違う 2 つのトークンに分けてこれを両立させる。頻繁に送るものは短命にし、長く持つものはめったに送らない、という分担である。

  • アクセストークン: API を呼ぶたびに送る。送り先が多く、露出する機会も多い。だから寿命を短く（数分〜十数分）する
  • リフレッシュトークン: アクセストークンが切れたときに、認可サーバーのトークンエンドポイントにだけ送る。露出する機会が少ないので、寿命を長くできる

時間の流れで見る

リフレッシュトークンを使うたびに、認可サーバーは「このユーザーとクライアントは、まだ許可されたままか」を確かめ直す。管理者がアクセスを取り消したり、ユーザーを無効にしたりすると、次の更新で新しいアクセストークンが出なくなる。手元に残ったアクセストークンも、長くて数分で切れる。

2 つのトークンの比較

観点アクセストークンリフレッシュトークン
送り先Web API（複数あり得る）認可サーバーのトークンエンドポイントだけ
送る頻度API を呼ぶたびアクセストークンが切れたときだけ
寿命の目安5〜15 分数時間〜数十日
誰が検証するかAPI。JWT なら認可サーバーに問い合わせずに検証する発行した認可サーバー自身。毎回、自分の記録と照合する
期限前の失効JWT では効きにくい（期限まで使える）即座に効く
クライアントとの結び付きなし（Bearer）発行先のクライアントに結び付く。Confidential client はクライアント認証が要る

リフレッシュトークンは寿命が長い代わりに、使われるたびに発行元が直接チェックできる。アクセストークンは検証が API 側で完結して速い代わりに、止められないので短くしておく。両者は互いの弱点を補い合っている。

盗まれたリフレッシュトークンを使わせない仕組み

リフレッシュトークンは寿命が長いぶん、盗まれたときの被害が大きい。そのため、RFC 6749 は、認可サーバーにリフレッシュトークンと発行先クライアントの結び付きを保つことを求めている。クライアントの種類によって守り方が変わる。

  • Confidential client（BFF など）: 更新のときにクライアント認証（client_secret、private_key_jwt など）が要る。リフレッシュトークンだけを盗んでも、クライアントの資格情報がなければ使えない
  • Public client（ブラウザ内の SPA など）: 資格情報がないので、トークンだけで使えてしまう。RFC 9700 は、ローテーションか送信者制約（DPoP など）のどちらかを求めている

ローテーションと再利用検知

ローテーションでは、リフレッシュトークンを使うたびに新しいものと交換し、古いものは使用済みにする。使用済みのトークンがもう一度使われたら、正規のクライアントか攻撃者のどちらかが古いトークンを持っている、つまり盗まれたと判断できる。認可サーバーはどちらが正規かを区別できないので、その系列のトークンをまとめて失効させる。

ローテーションは盗難を防ぐのではなく、検知して被害を止める仕組みである。攻撃者は、検知されるまでの間はアクセストークンを得られる。そのため、次の対策と組み合わせる。

  • 絶対的な有効期限: 更新を続けても、最初のログインから一定時間（例: 24 時間）で必ず切れるようにする
  • アイドルタイムアウト: 一定時間使われなかったリフレッシュトークンを失効させる
  • 送信者制約: DPoP で鍵に結び付け、トークンだけを持ち出しても使えないようにする（06 章）
  • ブラウザに置かない: BFF ならリフレッシュトークンはサーバーにあり、XSS で盗まれない（04 章）

スコープと audience

  • スコープ: トークンが許す操作の範囲。認可リクエストの scope パラメータで要求する（例: orders:read orders:write）。必要最小限だけ要求する
  • audience（aud）: トークンの宛先 API。宛先を限定すると、ある API に送ったトークンを別の API で使い回されない

スコープは「クライアントに許した範囲」であり、「ユーザーに許された範囲」とは別である。たとえば orders:read を持つトークンでも、他人の注文を読ませてはいけない。それを確かめるのは API 側の責任である（05 章）。

まとめ

  • SPA は Public client である。シークレットを持たず、PKCE を使う
  • SPA で使うグラントは認可コード + PKCE とリフレッシュトークンだけ。Implicit と Password は使わない
  • アクセストークンは短命の Bearer トークン。Authorization ヘッダーで送る
  • アクセストークンは短命で API に頻繁に送り、リフレッシュトークンは長命だが認可サーバーにだけ送る。失効は更新のときに効く
  • Public client のリフレッシュトークンは、ローテーションか送信者制約で守る
  • スコープはクライアントの権限、audience は宛先。ユーザーごとの権限確認は API が行う
