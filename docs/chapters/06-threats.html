SPA の最大の脅威は XSS である。XSS が起きれば、ブラウザの中のトークンはどこに置いても取られ得る。トークンの置き場所より先に XSS を防ぐ。Cookie を使うなら CSRF、別オリジンの API を呼ぶなら CORS も設計に入る。

トークンの保管場所

保管場所XSS で読めるかCSRF の影響評価
BFF のセッション（ブラウザには HttpOnly Cookie）トークンは読めない受ける。対策が必要推奨
Web Worker / Service Worker の中直接は読みにくい受けないブラウザ内方式なら最善
JavaScript のメモリ（変数・クロージャ）読める受けないブラウザ内方式の最低線。再読み込みで消える
sessionStorage / localStorage簡単に読める。localStorage はタブを閉じても残る受けない使わない
JavaScript から読める Cookie読める受ける使わない（両方の欠点を持つ）

XSS

XSS は、攻撃者の JavaScript を被害者のページで動かす攻撃である。トークンを盗むことも、被害者として API を呼ぶことも、偽のログイン画面を出すこともできる。

  • フレームワークの自動エスケープを崩さない。innerHTML、dangerouslySetInnerHTML、v-html を避ける。使うなら DOMPurify などで無害化する
  • 厳格な CSP を配信する（nonce ベースと strict-dynamic、object-src 'none'、base-uri 'none'）
  • 依存パッケージを監査する。サードパーティのスクリプトを同じページに読み込むと、それも同じ権限で動く
  • Trusted Types を使える環境なら有効にする
Content-Security-Policy: script-src 'nonce-r4nd0m' 'strict-dynamic'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'

CSRF

CSRF は、ブラウザが Cookie を自動で送る性質を悪用し、別サイトから被害者として操作させる攻撃である。Cookie で認証する BFF 方式では対策が要る。Bearer トークンだけで認証する API は、ブラウザが自動で付けないので影響を受けない。

  • セッション Cookie に SameSite=Lax 以上を付ける
  • 状態を変えるリクエスト（POST、PUT、DELETE）に、カスタムヘッダー（例: X-CSRF: 1）か CSRF トークンを要求する。カスタムヘッダー付きの別オリジンのリクエストは CORS のプリフライトで止まる
  • Origin ヘッダーを確かめ、自分のオリジン以外を拒否する
  • GET で状態を変えない

OAuth のフロー自体にもログイン CSRF がある。これは state と PKCE で防ぐ（02 章）。

Cookie の属性

Set-Cookie: __Host-session=9f8a...; Path=/; Secure; HttpOnly; SameSite=Lax
属性効果
HttpOnlyJavaScript から読めない。XSS による Cookie の持ち出しを防ぐ
SecureHTTPS でだけ送る
SameSite=Lax / Strict別サイトからのリクエストに Cookie を付けない（Lax はトップレベルの GET 遷移だけ許す）
__Host- 接頭辞Secure、Path=/、Domain なしを強制する。サブドメインからの上書きを防ぐ

CORS

CORS は、ブラウザが別オリジンへのリクエストの応答を JavaScript に読ませるかを、サーバーの許可で決める仕組みである。セキュリティを「緩める」ための仕組みであり、API を守る仕組みではない。

  • ブラウザ内方式（C）や Token-Mediating（B）では、Web API が SPA のオリジンを許可する必要がある
  • Access-Control-Allow-Origin は明示したオリジンに限る。* や、Origin ヘッダーをそのまま返す設定は使わない
  • Access-Control-Allow-Credentials: true を付けるなら、許可するオリジンはなおさら絞る
  • CORS は curl などブラウザ以外からのリクエストを止めない。認可は API が行う
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 600
Vary: Origin

BFF 方式で SPA と BFF を同一オリジンに置けば、CORS の設定自体が不要になる。

リフレッシュトークンのローテーション

ブラウザにリフレッシュトークンを渡すなら、使うたびに新しいものに替える。古いものが再び使われたら、盗まれたと見なして、その系列のトークンをすべて失効させる。

  1. 正規のクライアントが RT1 を使い、AT2 と RT2 を受け取る。RT1 は使用済みになる
  2. 攻撃者が盗んだ RT1 を使う
  3. 認可サーバーは使用済みの RT1 の再利用を検知し、RT2 を含む系列全体を失効させる

加えて、リフレッシュトークンに絶対的な有効期限（例: 24 時間）を設け、使い続けても永久には延びないようにする。

DPoP

DPoP（RFC 9449）は、トークンをクライアントの鍵ペアに紐付ける。リクエストのたびに秘密鍵で署名した DPoP ヘッダーを付けるので、トークンだけを盗んでも別の環境からは使えない。

  • ブラウザでは Web Crypto API で取り出せない鍵（extractable: false）を作り、IndexedDB に保管する
  • XSS で注入されたコードは、その場で署名させることはできる。DPoP が防ぐのはトークンの持ち出しであり、乗っ取りではない
  • 認可サーバーと API の両方が対応している必要がある

漏えい経路を減らす

  • トークン、認可コード、code_verifier をログやエラーレポート（Sentry など）に出さない
  • URL にトークンを載せない。コールバック後は URL から code を消す
  • コールバックのページから外部へのリンクや外部スクリプトを置かない（Referer で漏れる）。Referrer-Policy: no-referrer を付ける
  • リダイレクト URI を完全一致で登録し、オープンリダイレクターを作らない

まとめ

  • 先に XSS を防ぐ。どの構成でも、XSS が起きればユーザーとして操作される
  • Cookie を使うなら CSRF 対策（SameSite、カスタムヘッダー、Origin の確認）を入れる
  • CORS は許可の仕組みであり防御ではない。オリジンを明示し、認可は API で行う
  • ブラウザに渡すリフレッシュトークンはローテーションと絶対期限を必須にする。DPoP で持ち出しを防げる
