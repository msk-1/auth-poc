OpenID Connect（OIDC）は OAuth 2.0 の上に載る認証の仕様である。認可リクエストの scope に openid を含めると、アクセストークンに加えて、ログインしたユーザーを表す ID トークンが返る。

ID トークン

ID トークンは「どの IdP が、どのユーザーを、いつ、どのクライアントのために認証したか」を表す、署名付きの JWT である。

JWT の構造

JWT は . で区切られた 3 つの Base64URL 文字列からなる。

ヘッダー.ペイロード.署名
eyJhbGciOiJSUzI1NiIsImtpZCI6IjFlOWdkazcifQ.eyJpc3MiOiJodHRwczovL2F1dGguZXhhbXBsZS5jb20i...signature

// ヘッダー（作例）
{ "alg": "RS256", "kid": "1e9gdk7", "typ": "JWT" }

// ペイロード（作例）
{
  "iss": "https://auth.example.com",
  "sub": "248289761001",
  "aud": "spa-example",
  "exp": 1762590000,
  "iat": 1762589700,
  "auth_time": 1762589690,
  "nonce": "n-0S6_WzA2Mj",
  "amr": ["pwd", "otp"],
  "name": "Jane Doe",
  "email": "jane@example.com"
}

ペイロードは暗号化されていない。Base64URL を戻せば誰でも読める。秘密の情報を載せない。

主なクレーム

クレーム意味確かめること
iss発行者想定する IdP の URL と完全一致するか
subユーザーの識別子（IdP 内で一意・不変）アカウントの紐付けに使う
aud宛先クライアント自分の client_id を含むか
exp / iat有効期限 / 発行時刻期限が切れていないか
nonce認可リクエストで送った乱数自分が送った値と一致するか
auth_timeユーザーが実際に認証した時刻再認証が必要な操作で古すぎないか
acr / amr認証の強さ / 方式（パスワード、OTP など）MFA が必須の操作で要件を満たすか

ユーザーの紐付けは iss + sub で行う

email は変わることがあり、IdP によっては未確認のアドレスも入る。アカウントの紐付けを email で行うと、他人のアカウントに入れる場合がある。キーは iss と sub の組にする。

ID トークンの検証

クライアントは ID トークンを受け取ったら、次の順で検証する（OIDC Core 3.1.3.7）。

  1. JWKS から kid の公開鍵を取り、署名を検証する。alg は想定するもの（RS256 など）だけを受け入れる
  2. iss が IdP と一致する
  3. aud が自分の client_id を含む。複数の値を含むなら azp も確かめる
  4. exp が現在より未来である
  5. nonce が送った値と一致する

認可コードフローではトークンエンドポイントから直接受け取るので、TLS によって発行元は確かである。それでも nonce と aud の確認は省かない。

スコープとクレーム

スコープ得られるクレーム
openidsub（必須。これがないと OIDC にならない）
profilename、family_name、given_name、picture など
emailemail、email_verified
offline_accessリフレッシュトークンの発行を求める

UserInfo エンドポイント

アクセストークンを付けて呼ぶと、プロフィール情報を JSON で返す。ID トークンに入れなかったクレームを取るときに使う。

GET /userinfo HTTP/1.1
Host: auth.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCJ9...

応答の sub が ID トークンの sub と一致することを確かめる。

ディスカバリと JWKS

IdP の設定は {issuer}/.well-known/openid-configuration で公開されている。エンドポイントの URL は、ここから取得し、ハードコードしない。

{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "userinfo_endpoint": "https://auth.example.com/userinfo",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "end_session_endpoint": "https://auth.example.com/logout",
  "code_challenge_methods_supported": ["S256"],
  "id_token_signing_alg_values_supported": ["RS256", "ES256"]
}

jwks_uri は署名検証用の公開鍵の一覧を返す。IdP は定期的に鍵を替える（鍵ローテーション）。検証側は JWKS をキャッシュし、知らない kid が来たら取り直す。

ログアウト

ログアウトには 3 つの層がある。どれか 1 つだけでは「ログアウトしたつもり」になる。

層やること
アプリのセッションSPA のメモリや BFF のセッションを破棄する
トークンリフレッシュトークンを失効エンドポイントで無効にする（RFC 7009）
IdP のセッションend_session_endpoint にリダイレクトする（RP-Initiated Logout）。id_token_hint と post_logout_redirect_uri を付ける

IdP のセッションを残すと、次に「ログイン」を押したとき、パスワードを入れずにそのままログインできてしまう。共用端末では問題になる。

OpenID Federation

ここまでの OIDC は、RP と OP が1 対 1 で事前に関係を結ぶことを前提にしている。RP は OP にクライアント登録をして client_id を受け取り、OP の issuer を設定に書く。参加する組織が数十、数百と増えると、この組み合わせを個別に管理できなくなる。

OpenID Federation 1.0 は、参加者全員が信頼する第三者（Trust Anchor）を介して、初対面の RP と OP が互いを信頼できるようにする仕様である。2026 年 2 月に Final Specification として承認された。

00 章のフェデレーション（IdP ブローカー）とは別のものである。ブローカーはログインを中継する構成であり、OpenID Federation は参加者どうしの信頼を確立する仕組みである。

登場するエンティティ

参加者はすべてエンティティと呼ばれ、URL 形式の Entity Identifier で識別される。

エンティティ役割
Trust Anchor信頼の起点となる第三者。フェデレーションの運営者にあたる。参加者はその公開鍵を事前に持っている
IntermediateTrust Anchor と Leaf の間に入り、配下の参加者について署名する（例: 業界団体、大学の連合）
Leaf配下を持たないエンティティ。実際に OIDC を話す RP や OP がこれにあたる

Entity Configuration と Subordinate Statement

信頼の材料は Entity Statement と呼ばれる署名付き JWT である（typ は entity-statement+jwt）。次の 2 種類がある。

  • Entity Configuration: エンティティが自分自身について自己署名して公開するもの。{Entity Identifier}/.well-known/openid-federation から取得する。iss と sub は同じ値になる
  • Subordinate Statement: 上位のエンティティが直下のエンティティについて署名するもの。iss が上位、sub が配下になる。上位の federation_fetch_endpoint から取得する

RP の Entity Configuration のペイロードは、たとえば次のようになる（作例）。

{
  "iss": "https://rp.example.org",
  "sub": "https://rp.example.org",
  "iat": 1762560000,
  "exp": 1762646400,
  "jwks": { "keys": [ { "kty": "EC", "kid": "fed-1", "crv": "P-256", "x": "...", "y": "..." } ] },
  "authority_hints": ["https://intermediate.example.net"],
  "metadata": {
    "openid_relying_party": {
      "client_name": "Example RP",
      "redirect_uris": ["https://rp.example.org/callback"],
      "client_registration_types": ["automatic"],
      "token_endpoint_auth_method": "private_key_jwt",
      "jwks": { "keys": [ "..." ] }
    }
  }
}
  • jwks: Entity Statement の署名に使う鍵（フェデレーション用の鍵）
  • authority_hints: 自分の上位エンティティの一覧。チェーンをたどる手がかりになる
  • metadata: エンティティの種類ごとのメタデータ。openid_relying_party、openid_provider、federation_entity などがある。OP の場合、openid_provider の中身はディスカバリと同じ項目になる

Entity Configuration だけでは自己申告にすぎない。上位が Subordinate Statement で「この鍵はこのエンティティのものだ」と保証することで、はじめて信頼できる。

トラストチェーン

トラストチェーンは、対象エンティティの Entity Configuration から始まり、Trust Anchor で終わる Entity Statement の並びである。OP が上の図の RP を検証する場合は次のように組み立てる。

  1. RP の Entity Configuration を取得し、authority_hints から上位（Intermediate）を知る
  2. Intermediate の Entity Configuration から federation_fetch_endpoint を知り、RP についての Subordinate Statement を取得する
  3. 同じ手順で、Trust Anchor が Intermediate について発行した Subordinate Statement を取得する
  4. Trust Anchor の鍵（事前に持っているもの）から下に向かって署名を検証する。各ステートメントは、1 つ上のステートメントの jwks にある鍵で署名されている
  5. どれか 1 つでも署名、有効期限、iss と sub のつながりが合わなければ、そのエンティティは信頼しない

Trust Anchor の鍵さえ持っていれば、初めて見る RP でも鍵とメタデータを確かめられる。チェーンの組み立てを任せる federation_resolve_endpoint もある。

メタデータポリシー

上位のエンティティは、Subordinate Statement の metadata_policy で配下のメタデータを制約できる。演算子は value、add、default、one_of、subset_of、superset_of、essential である。たとえば Trust Anchor が「クライアント認証は private_key_jwt のみ」と決めると、配下の RP 全員に効く（作例）。

"metadata_policy": {
  "openid_relying_party": {
    "token_endpoint_auth_method": { "one_of": ["private_key_jwt"] },
    "grant_types": { "subset_of": ["authorization_code", "refresh_token"] }
  }
}

Leaf のメタデータに、上位から順にポリシーを適用した結果が、実際に使うメタデータになる。ポリシーに合わないメタデータを持つエンティティは信頼しない。

クライアント登録

方式やり方
自動登録（automatic）事前登録をしない。RP は自分の Entity Identifier を client_id として、署名付きのリクエストオブジェクトで認可リクエストを送る。OP はその場でトラストチェーンを解決して RP を検証する。クライアントシークレットは使えず、private_key_jwt などの非対称鍵によるクライアント認証が必須になる
明示的登録（explicit）RP が自分の Entity Configuration（またはトラストチェーン）を OP の federation_registration_endpoint に POST する。OP はチェーンを検証して client_id を発行する

トラストマーク

トラストマークは、エンティティが一定の基準を満たしていることを、認定機関（Trust Mark Issuer）が示す署名付き JWT である（typ は trust-mark+jwt）。Entity Configuration の trust_marks に載せる。たとえば「セキュリティ監査に合格した」「このプロファイルに準拠している」といった表明に使い、OP は特定のトラストマークを持つ RP だけを受け入れる、といった判断ができる。失効したかどうかは発行者の federation_trust_mark_status_endpoint で確かめる。

使いどころ

  • 向いている: 多数の組織の RP と OP が相互に接続する連携（学術機関の連合、公的サービスの連携など）。参加・脱退を運営者側の署名だけで管理できる
  • 不要: 自社の SPA と自社の IdP（Keycloak など）をつなぐ、あるいは少数の外部 IdP とつなぐ構成。通常のクライアント登録とディスカバリで足りる

よくある誤り

  • ID トークンを API に送る: ID トークンの aud はクライアントであり API ではない。API にはアクセストークンを送る
  • アクセストークンをログインの証拠にする: 別のクライアント向けに発行されたトークンを持ち込まれても区別できない（トークン置換）
  • 署名を検証せずにペイロードを読んで信じる: ペイロードは誰でも書き換えられる。表示に使うだけでも、検証した後にする

まとめ

  • scope=openid で OIDC になり、ID トークンが返る。ID トークンはクライアントが読むもの
  • 検証は署名、iss、aud、exp、nonce の順。ユーザーのキーは iss + sub
  • 設定はディスカバリから取り、公開鍵は JWKS から取る。鍵ローテーションに備える
  • ログアウトはアプリ、トークン、IdP の 3 層で行う
  • OpenID Federation は、Trust Anchor を起点とするトラストチェーンで、事前登録なしに RP と OP が互いを信頼する仕組みである
