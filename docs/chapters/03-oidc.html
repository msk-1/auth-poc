OpenID Connect（OIDC）は OAuth 2.0 の上に載る認証の仕様である。認可リクエストの scope に openid を含めると、アクセストークンに加えて、ログインしたユーザーを表す ID トークンが返る。

ID トークン

ID トークンは「どの IdP が、どのユーザーを、いつ、どのクライアントのために認証したか」を表す、署名付きの JWT である。

JWT の構造

JWT は . で区切られた 3 つの Base64URL 文字列からなる。

ヘッダー.ペイロード.署名
eyJhbGciOiJSUzI1NiIsImtpZCI6IjFlOWdkazcifQ.eyJpc3MiOiJodHRwczovL2F1dGguZXhhbXBsZS5jb20i...signature

// ヘッダー（作例）
{ "alg": "RS256", "kid": "1e9gdk7", "typ": "JWT" }

// ペイロード（作例）
{
  "iss": "https://auth.example.com",
  "sub": "248289761001",
  "aud": "spa-example",
  "exp": 1762590000,
  "iat": 1762589700,
  "auth_time": 1762589690,
  "nonce": "n-0S6_WzA2Mj",
  "amr": ["pwd", "otp"],
  "name": "Jane Doe",
  "email": "jane@example.com"
}

ペイロードは暗号化されていない。Base64URL を戻せば誰でも読める。秘密の情報を載せない。

主なクレーム

クレーム意味確かめること
iss発行者想定する IdP の URL と完全一致するか
subユーザーの識別子（IdP 内で一意・不変）アカウントの紐付けに使う
aud宛先クライアント自分の client_id を含むか
exp / iat有効期限 / 発行時刻期限が切れていないか
nonce認可リクエストで送った乱数自分が送った値と一致するか
auth_timeユーザーが実際に認証した時刻再認証が必要な操作で古すぎないか
acr / amr認証の強さ / 方式（パスワード、OTP など）MFA が必須の操作で要件を満たすか

ユーザーの紐付けは iss + sub で行う

email は変わることがあり、IdP によっては未確認のアドレスも入る。アカウントの紐付けを email で行うと、他人のアカウントに入れる場合がある。キーは iss と sub の組にする。

ID トークンの検証

クライアントは ID トークンを受け取ったら、次の順で検証する（OIDC Core 3.1.3.7）。

  1. JWKS から kid の公開鍵を取り、署名を検証する。alg は想定するもの（RS256 など）だけを受け入れる
  2. iss が IdP と一致する
  3. aud が自分の client_id を含む。複数の値を含むなら azp も確かめる
  4. exp が現在より未来である
  5. nonce が送った値と一致する

認可コードフローではトークンエンドポイントから直接受け取るので、TLS によって発行元は確かである。それでも nonce と aud の確認は省かない。

スコープとクレーム

スコープ得られるクレーム
openidsub（必須。これがないと OIDC にならない）
profilename、family_name、given_name、picture など
emailemail、email_verified
offline_accessリフレッシュトークンの発行を求める

UserInfo エンドポイント

アクセストークンを付けて呼ぶと、プロフィール情報を JSON で返す。ID トークンに入れなかったクレームを取るときに使う。

GET /userinfo HTTP/1.1
Host: auth.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCJ9...

応答の sub が ID トークンの sub と一致することを確かめる。

ディスカバリと JWKS

IdP の設定は {issuer}/.well-known/openid-configuration で公開されている。エンドポイントの URL は、ここから取得し、ハードコードしない。

{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "userinfo_endpoint": "https://auth.example.com/userinfo",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "end_session_endpoint": "https://auth.example.com/logout",
  "code_challenge_methods_supported": ["S256"],
  "id_token_signing_alg_values_supported": ["RS256", "ES256"]
}

jwks_uri は署名検証用の公開鍵の一覧を返す。IdP は定期的に鍵を替える（鍵ローテーション）。検証側は JWKS をキャッシュし、知らない kid が来たら取り直す。

ログアウト

ログアウトには 3 つの層がある。どれか 1 つだけでは「ログアウトしたつもり」になる。

層やること
アプリのセッションSPA のメモリや BFF のセッションを破棄する
トークンリフレッシュトークンを失効エンドポイントで無効にする（RFC 7009）
IdP のセッションend_session_endpoint にリダイレクトする（RP-Initiated Logout）。id_token_hint と post_logout_redirect_uri を付ける

IdP のセッションを残すと、次に「ログイン」を押したとき、パスワードを入れずにそのままログインできてしまう。共用端末では問題になる。

よくある誤り

  • ID トークンを API に送る: ID トークンの aud はクライアントであり API ではない。API にはアクセストークンを送る
  • アクセストークンをログインの証拠にする: 別のクライアント向けに発行されたトークンを持ち込まれても区別できない（トークン置換）
  • 署名を検証せずにペイロードを読んで信じる: ペイロードは誰でも書き換えられる。表示に使うだけでも、検証した後にする

まとめ

  • scope=openid で OIDC になり、ID トークンが返る。ID トークンはクライアントが読むもの
  • 検証は署名、iss、aud、exp、nonce の順。ユーザーのキーは iss + sub
  • 設定はディスカバリから取り、公開鍵は JWKS から取る。鍵ローテーションに備える
  • ログアウトはアプリ、トークン、IdP の 3 層で行う
